## What this is

Paths in the git index that collide on case — both case-variants are
tracked separately, but on Windows's case-insensitive filesystem only one
of each pair can physically exist on disk. Every git operation overwrites
whichever variant was last-written, and the index then shows the OTHER
variant as "modified" forever — which jams `git pull --rebase`.

Every collision below has **IDENTICAL** content on both sides (blob hashes
match), so removing one variant from the index is a zero-data-loss
operation. Verdicts of `DIFFERENT` (none in this scan) would indicate a
real content conflict that needs human resolution before dedupe.

## Why it happened

The sync scripts (`sync_*_unique.py`) write a file per wiki page title.
shinto.fandom.com / shinto.miraheze.org appear to have BOTH
`Template:Infobox <Type>` and `Template:Infobox <type>` titles in their
namespace — one canonical and the other a redirect (or a vestigial
duplicate). The sync follows both names verbatim and produces two files
in the repo. With Windows + `core.ignorecase=true`, those two files
collide.

## How to fix it (wiki-side, Emma's plan)

Find each `Template:Infobox <name>` pair on the wikis listed below;
delete or merge-redirect the lower-case variant so only the canonical
capitalised form remains. After the next sync run with one variant
removed, the index will naturally drop the orphan, and `core.ignorecase`
stops fighting us.
