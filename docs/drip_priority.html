Wikidata drip, in priority order

Drag the groups (or use the arrows) into the order you want them delivered, then press Save. Each bar shows where that group would finish if the drip worked through them in this order at 500 lines a day, with every run landing.

What reading the generators turned up

  • Several files never drop lines that already landed: reisai, bunrei and its hobby-site files, beppyo_p612, shintai, jinjacho_p973, hisousha, and the LLM-fed files. About 16,500 lines in all. The drip keeps drawing their finished lines as no-ops, which use up the day's 500. The wiki link files are frozen for the same reason. On 09-25 only 4% of draws were no-ops, so this is a growing cost, not yet a big one.
  • Bunrei has two layers that can disagree. The suffix-based files name the network head, not the actual parent shrine, and never check for an existing P612. So a shrine the accurate Beppyo layer already covers can get a second, conflicting P612.
  • Possible back-and-forth in Engishiki (unverified): 692 memberships that orphan_membership_removals removes are ones list_membership_rebuild adds back.
  • label_proposals_drip switches from 20 lines a day to its whole 2.78M-line pool on 2027-05-23. That would swamp the drip.
  • Pausing is safe for most files. Where one file waits on another it's marked ⚠ under the group, e.g. honzon → form removals, kana qualifiers → kana removals, typo fixes → multilingual fixes.
    Counts are lines staged on 2026-09-26. Most files are regenerated from live Wikidata, so they shrink as edits land.
